# BBO Capstone Dataset Datasheet
## Imperial Capstone — cumulative black-box optimisation dataset (Modules 12.1–20.1)

**Dataset status:** Cumulative record through Week 9 (Module 20.1)  
**Project:** Black-Box Optimisation (BBO) capstone  
**Functions:** Eight maximisation functions (F1–F8)

## 1. Motivation

### Why was this dataset created?
The dataset was created to support the BBO capstone, in which eight unknown objective functions are optimised through sequential query submissions. It preserves the original observations and the subsequent weekly input-output evaluations so that query decisions and optimisation progress can be reviewed over time.

### What task does it support?
It supports sequential, sample-efficient optimisation. The observed input-output pairs provide the evidence used to fit or assess Gaussian Process (GP) surrogate models and to consider acquisition strategies such as Expected Improvement (EI), Probability of Improvement (PI) and Upper Confidence Bound (UCB).

### Who created it and for what purpose?
The dataset was assembled by the capstone participant from the initial observations and actual weekly portal submissions. It is intended for the academic capstone analysis, strategy reflection and reproducible documentation of the participant's optimisation workflow.

## 2. Composition

### What does the dataset contain?
For each function, the cumulative record contains:
- Original input coordinates and their observed objective-function outputs.
- Weekly query coordinates and the actual outputs returned by the capstone portal.
- A chronological record identifying the observation source and whether it established a new best-observed value.

The original numerical observation arrays are retained in `.npy` format. The cumulative notebook records the weekly inputs and outputs in tabular form.

### Are there gaps or anomalous values?
The query distribution is non-uniform because later queries use information from earlier observations and promising regions. Consequently, substantial parts of some input spaces remain less explored, especially as dimensionality increases. This is a design characteristic of sequential optimisation, but it can create sampling bias and reduce confidence in predictions in sparsely sampled regions.

The recorded outputs have substantially different numerical scales across functions, and F1 includes values at very small magnitudes. This makes it important to interpret outputs within each function and to document any numerical scaling used when fitting a surrogate model. The current cumulative notebook does not establish a confirmed anomaly or symmetry pattern, so none is asserted here.

## 3. Collection process

### How were the queries generated?
Queries were submitted sequentially through the capstone portal. The cumulative dataset records the actual coordinates and returned outputs. The optimisation workflow considered the historical observations and function-specific query strategies, including GP-based reasoning and EI, PI and UCB.

The Week 9 allocation is explicitly recorded as:
- PI: F1 and F6.
- EI: F2, F4, F5 and F7.
- UCB: F3 and F8.

Week 8 allocations are also recorded in the cumulative analysis. The available record does not consistently document the acquisition allocation and all model settings for every earlier round; those details are not retrospectively inferred.

### What timeframe does it cover?
The dataset includes the original observations and nine successive weekly submissions, Modules 12.1–20.1. It is therefore a cumulative record through Week 9, not a completed Round 10 dataset.

### How were records validated?
Weekly input-output pairs were appended chronologically from the capstone submission records. The cumulative best was updated only when a new output exceeded the previous best. Since the functions are maximisation problems, this rule also applies to negative values.

## 4. Preprocessing and uses

### Were transformations applied?
The cumulative notebook documents the original coordinates and outputs. It does not establish that a single standardised preprocessing pipeline was applied to all stored observations. Any scaling or normalisation used during a particular GP fit should be documented in that model's notebook, including the transformation and whether it was applied to inputs, outputs or both.

The input domain is recorded as [0, 1] by design. Output magnitudes differ substantially across functions; cross-function comparisons of raw outputs are therefore inappropriate.

### Intended uses
- Reconstructing the participant's sequential BBO query history.
- Analysing best-observed progress within each function.
- Supporting GP surrogate modelling and acquisition-function experiments.
- Documenting query-selection reasoning, assumptions and limitations for the capstone.

### Inappropriate uses
- Treating best-observed values as proven global optima.
- Comparing raw objective values across different functions as though they shared a common scale.
- Assuming that an acquisition function caused an improvement based only on a small number of non-controlled observations.
- Using the dataset as a general-purpose benchmark without documenting its limited, sequential and non-uniform sampling design.

## 5. Distribution, access and maintenance

### Where is the dataset available?
The cumulative dataset is currently maintained in the participant's Capstone 20.1 notebook. The intended public distribution location is the participant's Imperial BBO capstone GitHub repository, subject to checking the programme's sharing rules before publication.

### Terms of use
The available capstone materials do not specify a separate licence for redistribution of the portal data. Before making the raw dataset public, the participant should check the Imperial programme and portal terms. Public GitHub publication should not imply that the underlying challenge data are unrestricted for reuse.

### Who maintains it?
The participant maintains the cumulative notebook and supporting records. New observations should be appended only after the corresponding portal outputs have been received and checked. Each update should preserve the original observations, chronological weekly history, source information and incumbent-best calculation.

### Maintenance and versioning recommendations
- Keep an unchanged copy of the original observations.
- Append new weekly query-output pairs rather than overwriting history.
- Record the module, round, date, acquisition strategy and relevant model settings for each new submission.
- Record missing metadata explicitly rather than reconstructing it from memory.
- Update the observation counts and best-observed summary after validating actual portal outputs.

---

## Dataset limitations statement

This datasheet describes the cumulative record available through Module 20.1 (Week 9). It does not claim that the dataset exhaustively covers any function's input space or that any recorded best is globally optimal. Some historical strategy and model-configuration details are incomplete in the available record. Those gaps should remain visible in any subsequent analysis.
