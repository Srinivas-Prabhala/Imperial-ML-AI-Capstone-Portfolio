# Model Card: GP-Supported Black-Box Optimisation Strategy
## Imperial Capstone — documented approach through Module 20.1 (Week 9)

## 1. Model overview

**Approach name:** Gaussian Process-supported sequential black-box optimisation  
**Approach type:** Surrogate-based, sequential, black-box optimisation  
**Documented status:** Cumulative experimental approach through Week 9 (Module 20.1)  
**Version:** Documentation baseline 1.0 (not a software release identifier)

The approach uses observed input-output pairs from eight unknown maximisation functions to inform subsequent query selection. Gaussian Process (GP) modelling provides a surrogate representation of a function and an estimate of predictive uncertainty. Acquisition functions considered in the capstone include Expected Improvement (EI), Probability of Improvement (PI) and Upper Confidence Bound (UCB).

This card describes the strategy evidenced in the cumulative capstone record. It does not assert that every model configuration, kernel or acquisition parameter is fully recorded for every round.

## 2. Intended use

The approach is intended for:
- Sequential optimisation when objective-function evaluations are limited or expensive.
- Using accumulated observations to guide subsequent query selection.
- Comparing candidate regions through predicted objective values and uncertainty.
- Documenting function-specific optimisation decisions in an academic capstone.

## 3. Uses to avoid

The approach should not be used to:
- Claim a global optimum solely from the best observed point.
- Treat GP predictions as actual objective-function evaluations.
- Assume EI, PI or UCB is universally best across functions.
- Compare raw output magnitudes across functions with different objective scales.
- Extrapolate confidently into sparsely sampled regions without considering posterior uncertainty.
- Make high-stakes operational decisions without independent validation and appropriate domain review.

## 4. Data and evaluation context

The model strategy is informed by eight functions with input dimensions from two to eight. The cumulative record through Week 9 contains 175 original observations and 72 weekly query evaluations, for 247 observations in total.

All input coordinates are recorded in [0, 1]. All functions are maximisation problems. The best-observed result is the highest recorded output for that function; it is not proof of the global maximum.

## 5. Strategy, techniques and evolution

### Overall workflow
1. Retain the original observations and append each weekly input-output pair chronologically.
2. Review the complete history for the function being optimised.
3. Fit or update a GP surrogate using the available observations.
4. Consider an acquisition function to balance exploitation of promising regions and exploration of uncertain regions.
5. Select a candidate query within the valid input domain.
6. Submit the query through the capstone portal and record the actual returned output.
7. Compare the result with the incumbent best and update the cumulative record only when the new output is higher.

### Acquisition functions
- **Expected Improvement (EI):** prioritises candidates with expected improvement over the current best, balancing predicted performance and uncertainty.
- **Probability of Improvement (PI):** prioritises the probability of exceeding the current best; depending on settings, it can favour exploitation near promising regions.
- **Upper Confidence Bound (UCB):** combines the posterior mean and uncertainty, with an exploration parameter controlling their relative contribution.

## 7. Assumptions

The approach relies on the following assumptions:
- Each function is a maximisation objective and the portal outputs are recorded accurately.
- Input coordinates are valid in the [0, 1] domain.
- The observed input-output pairs are informative about unobserved regions.
- A GP surrogate and its kernel assumptions provide a useful approximation over the sampled domain.
- The function is sufficiently stable between evaluations for historical observations to remain relevant.

If the function is noisy, discontinuous, non-stationary or poorly represented by the selected kernel, the GP posterior and acquisition ranking may be unreliable.

## 8. Constraints and limitations

- The number of evaluations is small relative to the size of the search space, particularly for higher-dimensional functions.
- Sequential queries are non-uniformly distributed and tend to concentrate around regions previously considered promising.
- GP predictions depend on kernel choice, hyperparameters, scaling and numerical conditioning.
- EI, PI and UCB depend on their parameterisation; UCB in particular requires an exploration parameter.
- Different functions have different dimensions and output scales.
- Some historical acquisition-function allocations and model settings are not fully documented in the cumulative record.
- The best-observed result is not a verified global optimum.
- Week 9 strategy outcome counts do not constitute a controlled comparison of acquisition functions.

## 9. Ethical considerations, transparency and reproducibility

The main transparency requirement is to preserve the complete input-output history and distinguish actual portal evaluations from model predictions or proposed candidates. Each query should be traceable to its function, round, coordinates, strategy and resulting output. Model configuration, preprocessing, software versions and random seeds should be recorded whenever available.

The approach is an academic optimisation exercise and should not be presented as a validated production system. Public release of portal data should be subject to the programme's data-sharing terms. Reproducibility is limited where historical model settings or strategy metadata are unavailable; these gaps should be disclosed rather than filled with assumptions.

## 10. Recommended future documentation

For each subsequent query, record:
- Function and round/module.
- Exact query coordinates.
- Acquisition function and its parameters.
- GP kernel and fitted hyperparameters.
- Input/output transformations, if any.
- Candidate-generation and optimisation procedure.
- Random seed and software versions, where relevant.
- Actual portal output and whether it improved the incumbent.

This information will make future model-card updates more complete and support stronger comparisons across rounds.
